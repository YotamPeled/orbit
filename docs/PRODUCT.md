# Orbit — what it is

Orbit is a **DevOps platform for one organization on its own server, built so an AI agent
can operate it**. You install one Orbit per organization: one machine, one k3s cluster,
one Grafana, one instance repo. Nothing is hosted and nothing is shared between orgs
except the code (this repository, the *core*).

> **A repo and one catalog entry in → a production service out.** A URL on the instance
> domain with TLS, dev and prod environments, Postgres whose password no human ever sees
> with point-in-time recovery, sealed secrets, metrics, logs and traces with a generated
> dashboard, alerts to Telegram — and `make verify`, which proves every one of those by
> running it, not by reading config.

**Operate, not drive.** An agent holding orbitd's MCP tools and the operator skills can
onboard a project, ship, roll back, diagnose, restore a database and silence an alert,
with the dangerous verbs behind a confirmation round. Agents acting on their own — woken by
an alert, fixing code — are V2 (docs/V1.md §9).

## How it works

```
 catalog/projects.yaml ──► scripts/catalog-sync.py ──► clusters/   (generated, committed)
        (the org's API)        + charts/service           │
                                                            ├─ platform apps ── applied from the DESK:
                                                            │                   orbit platform plan | apply
                                                            └─ tenant pairs ─── applied by ORBITD, in-cluster,
                                                                                every reconcile period
```

- **The catalog is the single registration point.** One project entry renders its
  namespaces, Deployments, Services, Ingress paths, NetworkPolicies, ResourceQuota,
  ServiceMonitors, the Postgres cluster, the generated RED dashboard and its probes. There
  is never a second place to register the same thing.
- **The desk** is the operator's machine. `scripts/desk.sh <command>` runs any desk
  command inside the `orbit-desk` image (kubectl, helm, sops, age, promtool, tofu and the
  `orbit` CLI), through an ssh tunnel to the node's API, which is firewalled from the
  internet. The platform layer — Traefik, cert-manager, CNPG, the observability stack,
  orbitd itself — is applied only from here: `orbit platform plan` shows the difference
  between git and the cluster, `orbit platform apply . --app <name>` applies one app.
- **orbitd** runs in the cluster. It is the control surface (an MCP server, protocol
  2026-07-28, OAuth 2.1 client credentials, Ed25519 tokens, roles viewer / operator /
  admin) and the applier for the tenant pairs: it renders each project/env from git and
  server-side-applies it, so git is the only way a tenant changes. docs/ORBITD.md.
- **Secrets** are sops+age sealed files under `clusters/platform/secrets/<ns>/<name>.yaml`
  in the instance repo, decrypted in the cluster by the sops-secrets-operator. Database
  passwords are generated by CNPG straight into Secrets. No vault, no human-held DB password.
- **Builds run on the operator machine**: `docker buildx build` + push to GHCR from a clean,
  pushed commit, then `orbit_deploy_ship` moves the tag. No CI is in the deploy path.
- **Proof** is `make verify` (stages 2–6): trust and edge, the generator and isolation,
  the secret plane, the observability planes, and that the live platform is the committed
  one. A check that cannot run is a failure, never a pass.

## Core vs instance

**Core (this repository, zero instance strings):** the catalog schema; the generator and
the service chart; the platform app definitions under `template/provisioning/`; the
verify stages; orbitd and the desk image; the operator skills (`skills/`) and the instance
skills (`.claude/skills/`); node bootstrap and the tofu modules.

**Instance (one small repo per org, from `template/`):** `instance/config.yaml` (domains,
DNS zones, node, registry, bucket, contacts), `catalog/projects.yaml` (the tenants), the
sealed secrets, and a vendored copy of core at the version pinned in `orbit-core.lock`
(`make core-sync`). `scripts/verify/no-instance-strings.py` greps everything core ships
for this instance's own values, so a leak fails the suite.

**Why one instance per org** (decided 2026-08-12, recorded so it is not relitigated):
isolation by physics instead of RBAC machinery, one org's blast radius per box, upgrades
rehearsed on one instance before the next. The verify suite is what makes many clusters
runnable by one person.

## What each platform component owns

| Component | Owns |
|---|---|
| k3s | the single-node cluster; kubelet reservations scaled to the node's RAM |
| Traefik | ingress, TLS termination, http→https, dev basic auth, the root span of every trace |
| cert-manager | one wildcard certificate per domain (DNS-01 at Cloudflare), renewed automatically |
| CloudNativePG + barman plugin | each declared Postgres: provisioning, generated credentials, WAL archive and nightly base backups to the bucket, point-in-time recovery |
| sops-secrets-operator | turning sealed files into Secrets |
| kube-prometheus-stack | Prometheus (7 d retention), Alertmanager (→ Telegram), Grafana, kube-state-metrics, node-exporter |
| Loki + Alloy | logs, collected from every pod, stored in the bucket |
| Tempo + OTel operator | traces: SDK injection per component `language:`, stored in the bucket |
| blackbox-exporter | probes of every public door (platform and tenant hostnames) |
| orbitd | the agent's control surface and the tenant applier |

## Sizing (measured 2026-10-11 on the rebuilt box, replaces every earlier estimate)

Measured on the test box (Hetzner cx43, 8 vCPU, 16 GB, k3s v1.36.5) after it was wiped and
rebuilt from bare by an agent on 2026-10-08, on orbit-core v0.34.34, with the V1 test tenant
running (one project, two environments, a database in each). From Prometheus:
`container_memory_rss` now, its maximum over the last 24 hours for the containers running
now (a pod started inside the day shows its own life only; orbitd had been upgraded an hour
before), and the memory each container requests and is limited to. The day measured was not
a quiet one: the alert and restart drivers of the V1 suite ran in it.

| Component | RSS now (MiB) | RSS 24 h max (MiB) | request (MiB) | limit (MiB) |
|---|---:|---:|---:|---:|
| Prometheus (+ config reloader) | 294 | 355 | 768 | 1536 |
| Grafana (+ dashboard sidecar, image renderer) | 263 | 271 | 672 | 1088 |
| Tempo | 238 | 471 | 384 | 1024 |
| orbitd (+ git-sync) | 135 | 157 | 160 | 256 |
| Loki | 112 | 216 | 384 | 768 |
| Alloy (+ config reloader) | 82 | 107 | 288 | 384 |
| cert-manager (3 pods) | 72 | 89 | 192 | 384 |
| Traefik | 46 | 48 | 96 | 256 |
| CNPG operator + barman plugin | 46 | 50 | 64 | 192 |
| Prometheus operator, kube-state-metrics, Alertmanager, blackbox, node-exporter | 117 | 130 | 280 | 624 |
| OTel operator, sops operator | 44 | 48 | 128 | 256 |
| k3s add-ons (coredns, metrics-server, local-path) | 54 | 56 | 140 | 170 |
| **platform containers, total** | **1503** | — | **3556** | **6938** |

Outside the platform's containers: the tenant's own pods (about 0.6 GiB), the k3s server,
containerd and the per-pod shims, and the kernel's own memory. **The whole box, with the
test tenant, uses 4.6 GiB** (`free -m` "used"); everything else is page cache the
kernel gives back on demand. The 24-hour maxima do not happen together — they are
per-component peaks.

What that means for a node:

- **8 GB is the floor.** The platform's requests (3.5 GiB) plus the system reservations
  leave room for a few small tenants on an 8 GB node (cx33).
- **16 GB (cx43) is comfortable** and is what the test box runs: the platform requests a
  quarter of allocatable, and a tenant set like the V1 test tenant fits several times over.
- The **platform memory budget alert** (`OrbitPlatformMemoryOverBudget`) fires when the
  platform's containers hold more than **2 GiB RSS** for 30 minutes — about a third above
  the 1503 MiB measured here, below any node's floor.

### The minimal profile (every optional feature off)

What Orbit cannot work without: Prometheus with its operator, Alertmanager,
kube-state-metrics and node-exporter, orbitd, cert-manager, Traefik, the sops operator and
the k3s add-ons. Measured on the same rebuilt box on 2026-10-11 (v0.34.34) with logs,
traces, dashboards, uptime and telegram alerts switched off through `orbit_features_set`
and read four times over half an hour once the box had settled:

| | RSS (MiB), last reading |
|---|---:|
| monitoring (Prometheus, operator, Alertmanager, kube-state-metrics, node-exporter) | 425 |
| orbit (orbitd + git-sync) | 135 |
| cert-manager | 71 |
| kube-system (coredns, metrics-server, local-path) | 55 |
| Traefik | 25 |
| sops operator | 15 |
| **platform containers, total** | **726** |

The four readings of that total: **704, 724, 718, 726 MiB**, with nothing firing but
the Watchdog: **about half the full profile's 1503 MiB**. Two things to know about this
number. The databases and backups features were left ON, because the test tenant has a
database and Orbit refuses to turn databases off under a project that declares one; their
operator's namespace (`cnpg-system`, 45 MiB in every reading) is measured and left out of
the total above, which is what turning them off would remove. And Prometheus was scraping
the tenant, which an empty platform would not: before the rebuild, on the same hardware with
no tenant and every feature off, the same total was 648 MiB and stayed between 601 and 663
over six hours (2026-10-07, v0.34.6). Turning one feature on adds what its row in the table
above says.

## Sizing a service

**The default.** A component that names no size gets **256Mi of memory, request and limit
alike, and its class's CPU request with no CPU limit** (`interactive`, the default class,
250m; `batch` 20m; `background` 10m: the chart's `defaultMemory` and `resourceClasses`). A
memory limit is always set; `memoryLimit` splits it from the request.

**The limits that protect the node** are two, and there is no per-service floor or ceiling:
the project's ResourceQuota (fitted to its catalog entry, below: a hand scale beyond it is
refused by the cluster) and the commit gate's `fit` check (a catalog change whose reservations
do not fit the node is refused before anything is applied, with the three numbers).

**Advice, not automation.** `orbit_size_recommend` (any role) answers, per component, what it
asks for, what it used over the last week, and a suggested request and limit with the reason:
memory is the peak plus 15%, CPU the 95th percentile plus 15% (the published method of Google's
Autopilot and the Kubernetes Vertical Pod Autoscaler). It never suggests less than the highest
use it has seen, gives no number for less than a day of history, and says so when memory use
does not show the need (a workload that sits at its limit was never seen with more room). An
agent or a person applies a size with `orbit_catalog_set`; nothing changes a running service on
its own. `OrbitWorkloadMemoryAtLimit` fires for a workload above 90% of its memory limit for 15
minutes. Automatic fitting is not part of V1 (docs/V1.md §9).

**What memory numbers cannot tell.** A runtime that sizes its own heap from the container limit
(.NET takes 75% of it, a JVM a quarter by default) refuses allocations when that heap is full,
which can be far below the container limit: measured on the test box, a .NET service was
throwing out-of-memory errors with its container at 56% of the limit. Neither the alert above
nor the advice can see that from memory use; it looks like room to spare, and the advice would
suggest less. What does see it is the error rate (`OrbitIngress5xxRateHigh` fired for that
service within ten minutes). So every suggestion to LOWER memory says to check the error rate
before and after, and for such a runtime the limit is chosen from its heap setting, not from
what the container was seen to use.

## Catalog behaviours worth knowing

**The ResourceQuota is fitted to the entry.** `catalog-sync.py` sums each component's
replicas × memory and CPU (the chart's defaults when a component names none), adds one
rolling-update surge pod of the largest `kind: web` component (`maxSurge: 1`), and adds the
database's declared memory and CPU. CPU is rounded up to the next half-core; pod count is
replicas + one surge + database instances + two for jobs and probes, with a floor of six.

**Per-environment overrides.** `projects[].environments.<env>.components.<name>` overlays
`replicas`, `cpu`, `memory`, `memoryLimit` and `drain` for that environment only. Unknown
keys and unknown component names are refused. The catalog default is the production shape;
an environment that needs less says so.

```yaml
environments:
  prod: {}
  dev:
    enabled: true
    components:
      api: {memory: 192Mi, replicas: 1}
```

**Database parameters.** `database.parameters` maps a Postgres GUC name (keys must match
`^[a-z_]+$`) to a string, rendered as `spec.postgresql.parameters` on the Cluster. Absent,
the Cluster has no `postgresql:` block.

```yaml
database:
  size: 2Gi
  memory: 256Mi
  parameters: {max_connections: "60", shared_buffers: "64MB"}
```

**Multi-domain.** An instance declares its domain set; a project renders on its declared
hostnames under the instance domains, and the generator refuses a domain the instance does
not declare. One wildcard certificate per domain; one probe per hostname.
