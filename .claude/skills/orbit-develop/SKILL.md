# Writing an application that runs on Orbit

This is the contract. `orbit-onboard` decides how a project is *declared*; this is what the
code itself must do. Every rule below names the failure it prevents, because a rule whose
reason is unknown is a rule that gets removed the first time it is inconvenient.

## The contract

### Run as a non-root UID

The chart pins `runAsUser: 65532` and **refuses to render** a component that would run as
root — a `fail`, not a warning. Namespaces additionally enforce the `restricted` Pod
Security standard as a backstop.

Put a `USER` line in the Dockerfile anyway. The orchestrator overrides it, so an image whose
only non-root story is that line is worth nothing — but with it, `docker run` behaves the way
the cluster does, and the difference between the two stops being a surprise you meet at
deploy time.

If the base image needs a specific UID (nginx 101, postgres 999), declare
`securityContext: {runAsUser: N}` in the catalog rather than patching the image. Overriding
with `null` does not work either: the chart strips nil overrides, because `mergeOverwrite`
wrote them straight through and silently handed identity selection back to the image.

### Configure from environment variables only

No config file baked into the image, no file read from disk at startup. A value that is not
an environment variable cannot be changed without a rebuild.

A variable is either a literal or a reference to a key in a Kubernetes Secret:

```yaml
env:
  LOG_LEVEL: info
  PGPASSWORD: {secret: widgets-db-app, key: password}
```

The reference names a **Kubernetes Secret and nothing else** — never a vault, never SOPS,
never CloudNativePG. All three producers terminate in an ordinary Secret, which is what lets
the secrets backend change without touching one line of application configuration.

### Take the database connection, never choose it

Credentials are generated by CloudNativePG and published as `<project>-db-app`. Read
`PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` and assemble the connection in code.
Do not invent a password, do not seal one into the repo by hand, do not write a connection string into
the catalog. There is no database credential for a human to leak, because there is no
database credential a human ever sees.

### Secrets locally: from the plane, and no `.env` files anywhere

Values live sealed in git and the cluster decrypts them, so a local process reads from
the plane, never from a file. The guardrails stay the same: prod values are read-only,
secrets are scoped per environment, and a laptop-only value has no route into the
cluster. A `.env` file is a secret in a working tree one `git add -A` away from being
a secret in a repository.

### Stateless by default; in-process state must declare `singleton`

If a restart or a second replica would lose something a user can see, the component must set
`singleton: true` in the catalog, and you must say so when handing the project over. The
platform cannot infer it, and the symptom is not a crash — it is a user being handed a
session the pod has never heard of, or a rolling update quietly dropping every request in
flight.

Prefer not needing it. State in Postgres survives deploys; state in a dictionary does not.

### Shut down on SIGTERM by finishing what you started

The platform owns the routing half of a graceful roll and cannot own the application half.

What the platform does, for every `web` component with a `port` that is not a `singleton`:
the pod is deleted, keeps serving for **5 more seconds** (a `preStop` sleep) while the
routers drop it from their pools, and only then gets `SIGTERM`, with **25 seconds** left
before `SIGKILL`. That window exists because a pod leaves the Service's endpoints and
leaves Traefik's load-balancer pool at two different times — measured at ~3s apart — and
without it, a rolling update 502s roughly half of the requests arriving in between, with
nothing wrong in any application log.

What your app must do with those 25 seconds: stop accepting new connections, finish the
requests already in flight, close the database pool, exit 0. Most frameworks do this for
you if you let them — `uvicorn`, `gunicorn` and ASP.NET all drain on `SIGTERM` — so the
usual mistake is not missing code but *added* code: a handler that calls `sys.exit()` or
`os._exit()` on the signal, or a container `command` wrapping the app in a shell that
takes the signal and never forwards it. Both turn a graceful roll back into a hard kill,
and the 5s sleep in front of it hides the damage from the router's view without fixing it.

If a request legitimately takes longer than 25s to finish, say so at handover — the budget
is a platform value, not something the catalog entry can raise.

### A health endpoint that does not depend on your database

`probePath` serves as both liveness and readiness. Make it prove the process is alive and
nothing more. A component whose readiness genuinely differs (still serving but must leave
rotation, e.g. while it rebuilds in-memory state) may set `readinessPath` for the
readiness probe alone; liveness keeps `probePath`. A component running with
`readOnlyRootFilesystem: true` that must write anything at runtime (temp files, caches)
declares `scratch: {mountPath, sizeLimit}` — a memory-backed writable volume.

A probe that checks Postgres turns "the leaderboard is briefly unavailable" into "nobody can
play, and the pods are being restarted for it." A game server whose engine holds live games
in memory should answer `/healthz` with 200 while the database is stopped, on purpose: only
the leaderboard degrades, and it should degrade loudly with a 500 rather than quietly with
an empty list.

### Logs to stdout; metrics at `/metrics`

Nothing is collected from files. Prometheus text format, and read
`orbit-onboard` §7 before deciding whether a number is a counter or a gauge.

Export a health gauge from **observed** failures, not only from a background probe. One
service's `<app>_database_up` was set every thirty seconds by a probe, and read `1` straight
through a real outage during which the endpoint that reads the database was returning 500. A
gauge that misses outages is worse than no gauge, because a dashboard is trusted.

### Schema is applied by the application, at startup, in the background

**There is no migration hook.** Earlier documentation described a `migrations:` key rendering
a PreSync hook; it was never built, and writing to a plan rather than to the code is how that
survived. What exists is what the services running here do: `CREATE TABLE IF NOT EXISTS` plus guarded
`ALTER`s, run from a background service that retries and never blocks startup.

That shape imposes three requirements:

1. **Idempotent.** It runs on every pod start, every restart, every deploy.
2. **Never fatal.** A database that is still bootstrapping must not crash-loop the app. Retry
   in the background and serve whatever does not need the database.
3. **Expand then contract.** Even a singleton runs old and new code against one database
   across a deploy. Renaming a column in one step breaks the pods still serving. Add a
   nullable column → write both → backfill → drop the old one, each a separate deploy. Four
   boring reversible steps beat one clever irreversible one.

`CREATE TABLE IF NOT EXISTS` is not a migration and does not verify anything. Against a
pre-existing table of the wrong shape it succeeds silently, and the service then reports
healthy while every write fails and reads return an empty list — a 200 with wrong data, the
worst answer available. Check `information_schema.columns` before declaring readiness.

### Two web components must not share a path

The chart refuses to render if they do. Kubernetes accepts duplicate paths silently and
Traefik then serves whichever it loaded last, so an SPA and its API both on `/` leaves the
SPA unreachable with no error anywhere.

Serve the front end from `/` and the API from `/api` on the same host, and the front end
needs no API hostname at all — a relative `/api` removes the cross-origin problem and removes
the rebuild required to move the API. Have the API accept the prefix (ASP.NET's
`UsePathBase`) rather than prefixing every route; the routes then read the same locally as in
the cluster.

### Calling another service inside the cluster

Use `http://<project>-<component>.<project>-<env>.svc` with no port. That is port 80, the
name every Orbit web Service publishes, and the one address to write down.

The chart also publishes the component's own container port on the same Service, because
the number a caller reaches for after reading a pod spec used to be a trap: kube-proxy only
programs the ports a Service declares, and a ClusterIP dialled on an undeclared port is not
refused — it is blackholed, and the caller hangs until its own timeout. That looked exactly
like a network policy denial and was not one. Both numbers now work; prefer the portless
form, and never a pod IP, which changes on every roll.

## The daily loop

### Run it locally against a real database

```bash
docker run -d --name pg -e POSTGRES_USER=app -e POSTGRES_PASSWORD=local -e POSTGRES_DB=app postgres:17-alpine
PGHOST=localhost PGUSER=app PGPASSWORD=local PGDATABASE=app <your run command>
```

Same variables the cluster injects. Nothing conditional on "am I in production" — that
branch is untested precisely where it matters.

### Edit → push → watch it land

**Nobody pushes directly to `dev` or `main`**, in this repo or any app repo here: work on
your own branch and land it through a reviewed pull request. Force-pushing a shared branch
is never the fix — it rewrites the history that is read back as the deploy record. The one
exception is orbitd's ship, which commits `catalog/tags.yaml` straight to `main` as the
org's GitHub App; nobody writes that file by hand.

`main` deploys to prod, `dev` to dev, unless the catalog says otherwise per environment.
A push builds nothing: once the commit is pushed and your tree is clean, build its image
on this machine and push it (`docker buildx build --platform linux/amd64 -t
<image>:<branch>-<sha7> --push .`), then ship the tag. An image built from a dirty tree
or an unpushed commit is never shipped: nobody else can read its source.

Watching it land is `orbit-ship`. The part that belongs to you: **the tag is a fact, not a
hope.** Compare the image the deployment is running to the tag the catalog declares before
believing a change is live.

### Read the logs

```bash
kubectl -n <project>-<env> logs deploy/<project>-<component> --tail=50 -f
kubectl -n <project>-<env> logs deploy/<project>-<component> --previous   # after a crash
```

`--previous` is the one people forget, and it is the only place a crash-loop's actual cause
survives.

### Debugging a pod that is running but wrong

Running-but-wrong is the common case, and every one of these has cost real time here:

- **Reaching another pod in the same namespace fails.** The default-deny NetworkPolicy admits
  the namespace's own pods, but if that rule is ever lost the symptom is a connection timeout
  that reads like a slow database or a bad password. Test it directly:
  `kubectl -n <ns> exec deploy/<app> -- bash -c 'echo > /dev/tcp/<host>/<port>'` — and note
  that is **bash**, not sh; `/dev/tcp` is a bash feature and `sh -c` reports a failure that
  is not real.
- **An environment variable is simply absent.** A missing `envFrom` Secret is skipped in
  silence. Check what the process actually got: `kubectl -n <ns> exec deploy/<app> -- env`.
- **The variable arrived renamed.** Go parses YAML 1.1, so an env key of `N`, `Y`, `ON` or
  `OFF` becomes a boolean and reaches the container called `"false"`. The schema now requires
  upper-case names, which catches it, because a coerced key always lowercases.
- **A CronJob's pod has no requests.** Every namespace carries a ResourceQuota, and a quota
  that names a resource makes it mandatory for every pod there. The workload is admitted and
  then rejected pod by pod, which surfaces as something that never runs rather than as an
  error.
- **The image is the old one.** The tag can be bumped in git while the pods still run the
  previous image — the rollout has not reached them yet. Compare the running image to the
  catalog tag (`orbit-ship` §4) before assuming anything is wrong.

### Rolling back

A deploy is a commit, so a rollback is `git revert` — landed on a branch through a reviewed
pull request like any other change, never pushed straight to `dev` or `main`. Never leave the
cluster and git disagreeing — the next apply carries whatever git says, so a
change made only in the cluster is a change that undoes itself.

## Before you call it done

- Does it run as a non-root UID, locally as well as in the cluster?
- Is every configurable value an environment variable?
- Does the health endpoint stay up when the database is down?
- Does the schema step retry rather than crash, and does it verify what it found?
- Is anything held in process memory declared `singleton`?
- Does a test go red when your fix is removed? A fix without one is a fix that gets deleted
  later by someone who cannot tell it was doing anything.
